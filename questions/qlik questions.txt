5 What are the different types of LOAD statements in Qlik Sense? Explain LOAD, INLINE, RESIDENT, FROM, and AUTOGENERATE with examples.

In Qlik Sense, the LOAD statement is used to load data into the Qlik data model, and we can also perform transformations while loading the data.

There are several commonly used approaches:

1. LOAD with FROM

FROM is used to specify an external data source such as a CSV, Excel, QVD, or other supported source.

For example:

LOAD
CustomerID,
CustomerName,
Amount
FROM [lib://Data/customer.csv]
(txt, utf8, embedded labels, delimiter is ',', msq);

2. INLINE LOAD

INLINE is used when we want to provide the data directly inside the Qlik script without using an external file or database.

For example:

LOAD * INLINE [
CustomerID, CustomerName
101, Babjee
102, Ravi
];

3. RESIDENT LOAD

RESIDENT is used to load data from a table that has already been loaded into the Qlik data model.

For example:

Sales:
LOAD
CustomerID,
Amount,
Quantity
FROM [lib://Data/sales.csv];

Sales_Transformed:
LOAD
CustomerID,
Amount,
Quantity,
Amount * Quantity AS TotalAmount
RESIDENT Sales;

4. AUTOGENERATE

AUTOGENERATE generates records based on an expression without requiring an external data source.

For example:

LOAD
RowNo() AS ID
AUTOGENERATE 10;

This generates 10 records.

It can also be used for generating dates, numbers, or other calculated values.

So, in simple terms:

FROM → loads from an external source

INLINE → data is written directly in the script

RESIDENT → loads from an already loaded Qlik table

AUTOGENERATE → generates records from expressions

LOAD → performs the actual loading and can also perform transformations.


6 synthetic key
A synthetic key is an automatically generated key created by Qlik Sense when two or more tables have two or more common fields.

For example, if Sales and Customer both contain CustomerID and ProductID, Qlik may create a synthetic key because there are multiple common fields between the tables.

Synthetic keys are not always errors, but they can indicate an undesirable or complex data model and may affect application performance.

To resolve a synthetic key, first I identify whether the common fields are actually required for the relationship.

I can resolve it by:

1. Renaming a field using an alias if the fields should not have the same name.
2. Dropping unnecessary duplicate fields from the load script.
3. Creating a composite key when multiple fields genuinely represent the relationship.

For example:

LOAD
CustomerID & '|' & ProductID AS CustomerProductKey,
Amount
FROM ...;

Then I can use CustomerProductKey as the common key between the tables.

I would not simply remove fields to eliminate the synthetic key. First I understand the business relationship and then choose the appropriate data-modeling solution.

7 What is the difference between JOIN, CONCATENATE, and KEEP in Qlik Sense?

JOIN combines two tables horizontally based on common fields. The result is a single table with columns from both tables.

For example:

Sales:
CustomerID, Amount

Customer:
CustomerID, CustomerName

If I JOIN Customer with Sales using CustomerID, the resulting table can contain:

CustomerID, Amount, CustomerName

CONCATENATE combines tables vertically by adding records from one table below another.

For example, if I have Sales2025 and Sales2026 with similar fields, I can concatenate them into one Sales table.

KEEP is different from JOIN. KEEP keeps the tables as separate logical tables, but reduces the records based on the common fields between the tables.

So the simple difference is:

JOIN → combines tables horizontally and creates one resulting table.

CONCATENATE → combines tables vertically by adding rows.

KEEP → keeps tables separate but reduces the data based on their association.

9 What is Set Analysis in Qlik Sense? Why do we use it? Explain the difference between Set Analysis and normal selections/filters with an example.
Set Analysis is an advanced feature in Qlik Sense that allows us to define a specific set of records for an aggregation.

We mainly use Set Analysis when we want to perform calculations based on specific conditions, and when we want the calculation to respect or ignore certain user selections.

For example:

Sum({<Year={2025}>} Sales)

This calculates Sales for the year 2025.

A Set Analysis expression generally contains a set identifier, set operators, and set modifiers.

The important set identifiers are:

$ → current selection

$1 → previous selection state

1 → all records, ignoring the current selection

For example:

Sum({1} Sales)

calculates Sales across the entire data set, regardless of the current selections.

Set Analysis is different from a normal filter because a filter changes the user's current selection, whereas Set Analysis controls the data set used specifically by an expression.

Set operators such as + can be used to create unions between sets.

10 What is a QVD? Why do we use QVDs in Qlik Sense? What are the main advantages of using QVDs?

QVD stands for QlikView Data file. It is Qlik's optimized data storage format used to store data extracted from different sources.

The main advantages of QVDs are:

1. Fast data loading — QVDs can be loaded much faster than many external sources because they use Qlik's optimized storage format.

2. Data compression — QVDs store data in a compressed format, which can reduce storage requirements.

3. Incremental loading — QVDs are commonly used in incremental-load architectures, where only new or changed records are extracted from the source.

4. Reusability — The same QVD can be used by multiple Qlik applications, reducing repeated extraction from source systems.

5. Transformed data — We can extract and transform data before storing it in a QVD, so downstream applications can consume prepared data.

QVDs are therefore commonly used as an intermediate or staging layer between source systems and Qlik Sense applications.

11 Now let's test incremental loading, which is a very common scenario question.

Suppose your source database contains 10 million sales records.

Every day, only 10,000 new records are added.

The interviewer asks:

“How would you implement incremental loading in Qlik Sense using QVD?”

Incremental loading is used when we have a large source table but only a small number of new or changed records are generated every day.

For example, if the source has 10 million records and only 10,000 new records are added daily, I don't want to extract all 10 million records every day.

The general approach is:

1. Check whether the QVD already exists.
2. Load the existing data from the QVD.
3. Identify only the new or changed records from the source using a field such as OrderID, CreatedDate, ModifiedDate, or UpdateTimestamp.
4. Load those incremental records from the source.
5. Combine the existing QVD data with the new or changed records.
6. Store the updated data back into the QVD.

This reduces source-system load and improves reload performance because we process only the required incremental data instead of performing a full load every time.

12 Your source table does not have a CreatedDate or UpdatedDate column. How will you implement incremental loading?”
If the source does not have a CreatedDate or UpdatedDate column, I can use a unique ID to identify newly inserted records.

I would load the existing QVD and compare the source IDs with the IDs already present in the QVD. Then I can load only the new IDs and concatenate them with the existing QVD data.

However, if the requirement is to capture updated records as well, comparing only the unique ID is not sufficient. In that case, I would need another mechanism, such as a source-side change tracking mechanism, CDC, audit table, modification information, or a suitable business rule.

So, with only a unique ID, I can reliably handle new records, but I cannot reliably detect changes to existing records.

13 What is a circular reference (loop) in Qlik Sense? Why does it occur, and how would you resolve it?

A circular reference, or loop, occurs in Qlik Sense when there are multiple association paths between tables, creating a loop in the data model.

For example, suppose we have:

Customer → Orders ← Product

and Customer is also directly associated with Product.

Now there can be more than one path between Customer and Product, which can create a circular reference.

To resolve it, I first identify which associations are actually required from a business perspective.

Possible solutions are:

1. Rename fields using aliases when fields should not be associated.
2. Drop unnecessary common fields from the load script.
3. Redesign the data model to remove the unwanted association.
4. Use a Link Table when multiple relationships are genuinely required.

I would not simply remove a field just to eliminate the loop. I would first understand the business relationship and then choose the appropriate modeling solution.

14 What is a Link Table in Qlik Sense? When would you use a Link Table? Explain with a practical example.
A Link Table is a bridge table used in Qlik Sense to connect multiple tables through common keys while avoiding unwanted associations, synthetic keys, or circular references.

For example, suppose we have two fact tables:

Sales:

* CustomerID
* ProductID
* SalesAmount

Returns:

* CustomerID
* ProductID
* ReturnAmount

Both fact tables need to be associated with Customer and Product dimensions.

Instead of directly connecting everything and potentially creating an undesirable data model, I can create a Link Table containing the required common keys, such as CustomerID and ProductID, and use it as a bridge between the fact tables and dimensions.

A Link Table is particularly useful when multiple fact tables share dimensions or when we have complex many-to-many relationships.

So, I would use a Link Table as a data-modeling technique to control associations and avoid problems such as circular references or synthetic keys.


15 Now let's test ApplyMap(), one of the most frequently asked Qlik scripting questions.
ApplyMap() is a Qlik Sense scripting function used to look up a value from a mapping table based on a key.

For example, if the Employee table contains DeptID and I want to get DeptName from a Department mapping table, I can use ApplyMap().

First, I create the mapping table:

DeptMap:
MAPPING LOAD
DeptID,
DeptName
FROM [lib://Data/department.csv];

Then, while loading Employee, I use:

Employees:
LOAD
EmpID,
DeptID,
ApplyMap('DeptMap', DeptID, 'Unknown') AS DeptName
FROM [lib://Data/employees.csv];

Here, Qlik takes the DeptID from each employee, looks it up in DeptMap, and returns the corresponding DeptName.

ApplyMap() is often preferred over a JOIN for simple lookups because it adds only the required value to the target table and avoids creating an additional joined table.

16 What is the difference between ApplyMap() and JOIN in Qlik Sense? When would you choose ApplyMap() over a JOIN?

JOIN combines columns from two or more tables and produces a single resulting table.

ApplyMap(), on the other hand, does not physically combine the mapping table with the current table. It performs a lookup using a key and returns the corresponding value.

For example, if Employee has DeptID and I need DeptName, I can create a mapping table with DeptID and DeptName and use ApplyMap() to retrieve DeptName.

I would generally prefer ApplyMap() when I need a simple lookup value from a reference table because it is more targeted and avoids physically joining the tables.

JOIN is more appropriate when I actually need multiple fields from another table or need to combine the tables as part of the data model.

So, in simple terms:

JOIN → physically combines tables.

ApplyMap() → performs a key-based lookup and returns a value.

19 What is the difference between Sum() and Aggr() in Qlik Sense?

Give me a simple example where Aggr() is required but Sum() alone would not solve the problem.

`Sum()` is an aggregation function used to calculate the total of a numerical field based on the current selection.

`Aggr()` is used when we need to perform an aggregation at a specific dimensional level and then apply another aggregation on the result. It creates a virtual table or array based on the dimensions we provide.

For example, if I want to calculate the average sales per customer:

`Avg(Aggr(Sum(Sales), Customer))`

Here, `Aggr()` first calculates total sales for each customer, and then the outer `Avg()` calculates the average of those customer-level totals.

So, simply:

* `Sum()` → directly aggregates values.
* `Aggr()` → creates an aggregated result at a specified dimension level, which can then be used by another aggregation.

21 What is the difference between $, $1, and 1 in Qlik Sense Set Analysis?
In Qlik Sense Set Analysis:

* `$` represents the **current selection state**.
  Example: `Sum({$} Sales)` calculates sales based on the user's current selections.

* `1` represents **all records**, ignoring the current selections.
  Example: `Sum({1} Sales)` calculates sales from the complete dataset.

* `$1` represents the **previous selection state**.
  Example: `Sum({$1} Sales)` calculates sales based on the previous selection state.

So, simply:

`$` → Current selection
`1` → Ignore current selection
`$1` → Previous selection

22 What is the difference between WHERE and IF in a Qlik Sense LOAD statement?

`WHERE` is used to filter records during the load process. Records that do not satisfy the condition are not loaded into the Qlik data model.

For example:

```qlik
LOAD
    CustomerID,
    CustomerName
FROM [lib://Data/customers.csv]
WHERE NOT IsNull(CustomerID);
```

Here, records with a null `CustomerID` are excluded from the data model.

`IF()` is used to evaluate a condition and return a value based on that condition. It is commonly used to create calculated or derived fields.

For example:

```qlik
LOAD
    CustomerID,
    NumberOfChildren,
    IF(NumberOfChildren > 0, 'Yes', 'No') AS IsParent
FROM [lib://Data/customers.csv];
```

Here, `IF()` returns `Yes` when the customer has children; otherwise, it returns `No`.

So, simply:

`WHERE` → filters records during loading.

`IF()` → evaluates a condition and returns a value.

23 What is the difference between RESIDENT LOAD and FROM LOAD in Qlik Sense?

`FROM` is used to load data from an external data source such as a CSV file, Excel file, QVD, or database.

`RESIDENT LOAD` is used to load data from a table that has already been loaded into Qlik's memory.

    Price
FROM [lib://Data/Sales.csv];

LOAD

27 Let's move to Qlik Sense data modeling.

Dimensional modeling generally consists of Fact and Dimension tables.

A **Dimension table** contains descriptive attributes that are used to analyze, filter, and group data. For example, a Customer dimension can contain CustomerID, CustomerName, City, and Region.

A **Fact table** contains transactional or measurable data. It normally contains foreign keys referencing dimensions along with numerical measures such as Quantity, SalesAmount, and Profit.

For example, in a Sales model:

```text
DimCustomer
     |
     |
 FactSales ---- DimProduct
     |
     |
  DimDate
```

The FactSales table may contain CustomerID, ProductID, DateID, Quantity, and SalesAmount, while the dimension tables contain descriptive information about customers, products, and dates.

Typically, a fact table contains a much larger number of records than dimension tables.

So, simply:

**Dimension → Descriptive information**

**Fact → Measures + keys to dimensions**
