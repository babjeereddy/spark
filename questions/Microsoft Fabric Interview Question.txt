Microsoft Fabric Interview Questions & Answers
1. What is Microsoft Fabric?

Answer:

Microsoft Fabric is an end-to-end SaaS analytics platform from Microsoft that integrates data engineering, data integration, data warehousing, data science, real-time analytics, and Power BI into a single platform.

Main workloads
Data Factory – Data integration and pipelines
Data Engineering – Spark, notebooks, Lakehouse
Data Warehouse – SQL-based analytics
Data Science – Machine learning
Real-Time Intelligence – Streaming and real-time analytics
Power BI – Reporting and visualization

Interview point:

"Microsoft Fabric provides a unified analytics platform where data can be ingested, transformed, stored, analyzed and visualized using a common data foundation called OneLake."

2. What is OneLake?

Answer:

OneLake is the centralized data lake for Microsoft Fabric.

Think of it as:

                Microsoft Fabric
                       |
                    OneLake
                       |
        --------------------------------
        |              |               |
     Lakehouse      Warehouse     Other workloads
        |
     Files/Tables

OneLake provides a single logical data lake across the organization.

Key points
Built into Fabric
Organization-wide data lake
Uses Delta Lake for Fabric Lakehouse tables
Reduces data duplication
Supports multiple Fabric workloads
Interview answer

"OneLake is the single, centralized data lake of Microsoft Fabric. It provides a common storage layer for Fabric workloads and eliminates the need for every team to maintain separate data lakes."

3. What is a Lakehouse?

Answer:

A Lakehouse combines the capabilities of a Data Lake and Data Warehouse.

It allows us to store:

Files
Structured data
Semi-structured data
Tables

A Fabric Lakehouse has two major areas:

Lakehouse
   |
   +---- Files
   |
   +---- Tables
Files

Used for raw/unstructured or semi-structured data:

CSV
JSON
Parquet
Excel
Tables

Used for structured analytical data.

Fabric Lakehouse tables are generally stored using Delta Lake format.

4. What is a Warehouse in Microsoft Fabric?

Answer:

Fabric Warehouse is a SQL-based analytical data store designed primarily for structured relational data and analytical workloads.

You can use T-SQL to:

Create tables
Create views
Query data
Create stored procedures
Perform analytical queries

Example:

SELECT
    CustomerID,
    SUM(SalesAmount) AS TotalSales
FROM Sales
GROUP BY CustomerID;
Lakehouse vs Warehouse
Lakehouse	Warehouse
Data lake + tables	SQL analytical warehouse
Supports files and tables	Primarily structured tables
Spark + SQL	T-SQL
Data engineering friendly	SQL/BI friendly
Good for raw + curated data	Good for curated relational data
5. What is the SQL Endpoint?

This is an important interview question.

Answer:

The SQL analytics endpoint is the SQL interface provided for querying tables in a Fabric Lakehouse.

For example, if your Lakehouse contains:

Customer
Product
Sales

you can query them using SQL.

SELECT *
FROM Sales;
Important distinction

Don't confuse:

Lakehouse SQL Analytics Endpoint

with

Fabric Warehouse.

The Lakehouse SQL endpoint provides read-oriented SQL access to Lakehouse tables, whereas a Fabric Warehouse is a separate SQL-based data warehouse workload.

12. What is Filter Activity?

Answer:

Filter activity is used to filter an array of items based on a condition inside a pipeline.

For example, suppose a Lakehouse folder contains:

employee.csv
customer.csv
sales.xlsx
product.json
department.csv

We only want .csv files.

Filter expression:

@and(
    equals(item().type,'File'),
    endsWith(toLower(item().name),'.csv')
)

Result:

employee.csv
customer.csv
department.csv
Interview explanation

"I use Filter activity when I have a collection of items and want to continue processing only the items that satisfy a particular condition."

13. What is item() in Fabric Pipeline?

Answer:

item() represents the current item being processed in activities such as Filter and ForEach.

For example:

employee.csv
customer.csv
sales.xlsx

When processing:

employee.csv

item().name returns:

employee.csv

Similarly:

item().type

returns the type of the current item.

Interview answer

"Pipeline parameters help make pipelines reusable, dynamic and configurable instead of hardcoding values."

17. What is Streaming Data?

Answer:

Streaming data is continuously generated data that arrives as a sequence of events rather than as a single batch.

Example:

10:01:01 → Sensor = 25°C
10:01:02 → Sensor = 26°C
10:01:03 → Sensor = 27°C
10:01:04 → Sensor = 29°C

Instead of waiting until the end of the day, we process the events continuously.

Batch vs Streaming
Batch	Streaming
Data processed periodically	Data processed continuously
Minutes/hours/days	Seconds/milliseconds
Daily sales report	Live sensor monitoring
ETL jobs	Event processing

In Microsoft Fabric + Power BI, Row-Level Security (RLS) is implemented in the semantic model. It controls which rows a user can see, not which tables or columns they can access.

1. Simple example

Suppose your Sales table contains:

SaleID	Region	SalesAmount
1	South	10000
2	North	15000
3	South	12000
4	West	18000

You want:

South manager → only South data
North manager → only North data
West manager → only West data
2. Create a security mapping table

For a real project, I recommend dynamic RLS.

Create a table such as:

UserRegion
UserEmail	Region
ravi@company.com	South
kumar@company.com	North
anil@company.com	West

Your model becomes:

UserRegion
    |
    | Region
    ↓
  Region
    |
    | 1 : *
    ↓
  Sales

Or, if you don't have a separate Region dimension:

UserRegion
    |
    | Region
    ↓
   Sales
3. Create the relationship

In the semantic model, create:

UserRegion[Region]
        1
        |
        *
Sales[Region]

Use the appropriate relationship/filter direction so the security filter can propagate from the security table to Sales.

A dimension-based star schema is generally preferable for production models.

4. Create the RLS role

Open your semantic model and go to:

Modeling → Manage roles

Create a role:

SalesSecurity

Apply a filter to the UserRegion table:

[UserEmail] = USERPRINCIPALNAME()
What does this do?

Suppose the logged-in user is:

ravi@company.com

Power BI evaluates:

USERPRINCIPALNAME()

and gets:

ravi@company.com

Therefore the security table becomes:

UserEmail	Region
ravi@company.com	South

Through the relationship, only:

South

Sales rows are visible.

5. Test the RLS

In Power BI/Fabric, use:

Security / Test as role

Test with different users/roles.

For example:

ravi@company.com
       ↓
South
       ↓
Only South Sales
6. Publish to Fabric

Once your report and semantic model are ready:

Power BI Desktop
       ↓
Publish
       ↓
Fabric Workspace
       ↓
Semantic Model

The RLS role is part of the semantic model.

7. Assign users to the role

This is a very important interview point.

Creating the role is not enough.

You must assign users or groups to the role in the Fabric/Power BI service.

Conceptually:

SalesSecurity Role
       |
       +---- ravi@company.com
       +---- kumar@company.com
       +---- anil@company.com

For an enterprise environment, using a security group is usually easier than maintaining individual users.

8. Static vs Dynamic RLS
Static RLS

You hardcode the region:

[Region] = "South"

This role can see only South.

South Role
    ↓
South data

This works for small/simple scenarios.

Dynamic RLS

Instead of creating separate roles for every region, use the logged-in user's identity:

[UserEmail] = USERPRINCIPALNAME()

Example:

User                 Region
--------------------------------
ravi@company.com     South
kumar@company.com    North
anil@company.com     West

One role can handle all users.

Interview answer

"Static RLS uses fixed filter values such as Region = 'South', whereas dynamic RLS uses the logged-in user's identity, such as USERPRINCIPALNAME(), to determine which rows the user can access."

9. Important interview scenario
Interviewer:

"Suppose I have 1,000 users and 20 regions. Would you create 20 RLS roles?"

Good answer:

"No. I would preferably implement dynamic RLS using a user-to-region mapping table. The mapping table would contain the user's email and permitted region. I would create one RLS role using USERPRINCIPALNAME(). The user's identity filters the mapping table, and the relationship propagates the filter to the Sales fact table."

Architecture:

             Logged-in User
                    |
                    ↓
          USERPRINCIPALNAME()
                    |
                    ↓
             UserRegion
          +----------------+
          | Email | Region |
          +----------------+
                    |
                    ↓
                Region
                    |
                    ↓
                 Sales
                    |
                    ↓
             Power BI Report
10. What if one user has multiple regions?

This is another excellent interview question.

Example:

UserEmail	Region
manager@company.com	South
manager@company.com	West

The same user can therefore see:

South + West

The dynamic RLS filter:

[UserEmail] = USERPRINCIPALNAME()

returns both rows.

11. RLS vs Object-Level Security

Don't confuse them.

RLS	OLS
Controls rows	Controls tables/columns
User sees selected rows	User may not see certain objects
Example: only South sales	Example: hide Salary column

RLS example:

Sales
 ├── South ← User can see
 ├── North ← Hidden
 └── West  ← Hidden
